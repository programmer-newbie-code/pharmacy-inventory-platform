# Release v1.8.0

Child increment of
[`cross-agent modernization roadmap`](2026-08-12-cross-agent-modernization-roadmap.md)
release automation.

## Evidence

Audited at `503ce3d`.

- Latest tag is `v1.7.0`, published 2026-08-09.
- `git log v1.7.0..origin/main` contains **40 commits**: 22 user-visible
  (`feat`/`fix`/`localize`) and 18 supporting (`docs`/`chore`/`ci`/`test`).
- Main CI run `31669255974` is green for `503ce3d`.
- No open PRs.
- `CHANGELOG.md` stops at `1.3.5` while `pubspec.yaml` reads `1.7.0+11`, so
  four releases shipped without a changelog entry.

Everything merged since `v1.7.0` is therefore on `main` but reaches no user.

## Goal

Publish `v1.8.0` so the merged work reaches users, and make the changelog an
accurate record again.

## Scope

- An annotated `v1.8.0` tag on green `main`.
- `CHANGELOG.md` entries covering `1.4.0` through `1.8.0`, written in
  user-facing language rather than commit subjects.
- Handoff status updated with the release evidence.

## Versioning mechanism

`docs/release/RELEASE_CHECKLIST.md` states plainly: **do not manually edit
`pubspec.yaml`.** CI derives the version from the tag
(`.github/workflows/ci.yml`, "Auto-Inject Dynamic Version"): for a `refs/tags/v*`
ref it strips the leading `v` and appends the run number as the build number.
The `chore: bump version` commits in this repository's history predate that
automation and must not be imitated.

`v1.8.0` rather than `v1.7.1`, because the range contains new features
(report exports, supervisor shift review, brand identity), not only fixes.
`v2.0.0` is not warranted: no schema migration is destructive and no documented
behaviour was removed.

## Non-goals

- Editing `pubspec.yaml`.
- Google Play submission. Store identity, signing-key custody, and publication
  are owner-only actions and remain external.
- Finishing the localization sweep. 22 plain and 34 interpolated strings remain
  and are tracked separately; none are user-visible defects, since all are
  English-only in an English build.
- Windows or Android visual refinement, which needs rendered comparison and
  owner approval.

## Acceptance criteria

1. `CHANGELOG.md` has an entry for every released version from `1.4.0` to
   `1.8.0`, each describing user-visible outcomes.
2. No diff to `pubspec.yaml`.
3. The tag is annotated and created on a `main` commit whose CI is green.
4. Tag CI completes green, including `analyze-and-test`, `build-windows`,
   `build-android`, secret scan, and signature verification.
5. `create-release` publishes the Windows and Android artifacts, and the release
   appears in `gh release list`.
6. The handoff status file records the released tag, the run that verified it,
   and the artifact evidence.

## Risks and controls

- **Tagging an unverified commit:** confirm the target commit's main CI run is
  green before tagging, not after.
- **Publishing a broken artifact:** the tag pipeline runs the same
  analyze/test/coverage gates plus both platform builds; a red pipeline means no
  release is published and the tag can be deleted and recreated.
- **Changelog drift recurring:** the missing `1.4.0`-`1.7.0` entries are
  reconstructed from merged PRs in this increment so the file is trustworthy
  again.
- **Unverified smoke testing:** `docs/release/RELEASE_CHECKLIST.md` requires a
  manual Windows and Android smoke test. No Flutter toolchain or device is
  available in this environment, so that step is explicitly **not** done here
  and remains an owner action before distributing the artifacts. This is
  recorded rather than silently skipped.

## Verification strategy

Tag CI is the gate. Post-tag, confirm the release exists with its Windows and
Android assets attached, and record the run id. Manual smoke testing on real
Windows and Android devices stays an owner action.
